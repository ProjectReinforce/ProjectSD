3. "캡슐화" 응집도와 결합도
모든 버그는 응집도가 낮거나, 결합도가 높은 환경에서 쉽게 발생한다.
징후들을 무시하고 개발을 하면 기술 부채가 쌓이고 유지보수가 점점 힘들어진다.


응집도/결합도가 뭘까 - 참여유도

맞추기 전까지 낮은 징후 아래 내용은 가릴것

응집도가 낮다: 이곳의 역할이 다른곳들에 분산됐다(Shotgun Surgery, anemic domain model), 여러 역할이 이곳에 섞여 있다(GodClass)
응집도가 높다: 변경 이유가 같은 코드는 한곳에 모여 있고, 다른 이유로 바뀌는 코드는 분리되어 있다
├── godclass 예방 SRP(바뀌는 이유가 하나인 클래스)
└── 데이터 중복 제거(Don't Repeat Yourself)
[변경 A]
 └ 이 변경 때문에 수정해야 할 코드들
    ├ A1
    ├ A2
    └ A3

맞추기 전까지 높은 징후 아래 내용은 가릴것


결합도가 높다: 한 곳의 변경이 다른 모듈로 전파된다. 떼었다 붙이기 어렵고, 작은 수정이 컴파일 에러나 부작용으로 이어진다
결합도가 낮다 : 한 곳을 수정해도 다른 곳을 수정할 필요가 없다
├── ADP (Acyclic Dependencies Principle)입니다.Robert C. Martin, 패키지 설계 원칙: "의존 그래프에 순환이 있어서는 안 된다")
├── DIP/OCP: 구체 구현보다 추상화에 의존해 변경 전파를 줄인다



공개후 캡슐화 와 자기만의원칙/예방법 참여유도

DI 시점에 유효성검사 (Fail Fast)
의존성은 생성자/파라미터로 명시해라	결합도	숨겨진 의존을 드러내서 관리 가능하게

6. 핵심 아이디어

많은 설계 문제는 두 개념으로 설명할 수 있다.

응집도 (Cohesion)
결합도 (Coupling)

많은 안티패턴과 개발자 밈도
결국 이 두 개념이 깨졌을 때 발생한다.

7. 책임을 판단하는 방법

우리는 보통 주제나 기능으로 책임을 판단한다.

SkillManager
 ├ 데미지 계산
 └ 이펙트 출력

둘 다 스킬과 관련된 기능이므로
응집도가 높은 설계처럼 보인다.

8. SRP

하지만 SRP는 이렇게 말한다.

A class should have only one reason to change

책임은 기능이 아니라
바뀌는 이유 (reason to change) 로 판단한다.

예

데미지 계산 → 게임 밸런스 변경
이펙트 출력 → 연출 변경

9. 응집도

응집도

같은 이유로 바뀌는 코드를 한곳에 모으고
다른 이유로 바뀌는 코드는 분리하는 것

응집도가 낮을 때 나타나는 징후

God Class

Shotgun Surgery

Anemic Domain Model

10. 응집도가 높은 구조

응집도가 높은 구조에서는

같은 이유로 변경되는 코드가
같은 모듈 안에 모여 있다.

[변경 A]
 └ 수정해야 할 코드
    ├ A1
    ├ A2
    └ A3
11. 결합도

결합도

한 곳의 변경이 다른 곳으로
퍼지지 않게 하는 것

결합도가 높을 때 나타나는 징후

하나 수정하면 여러 곳에서 오류 발생

작은 수정이 예상치 못한 부작용 발생

코드를 재사용하거나 분리하기 어렵다

12. 결합도를 낮추는 방법

결합도를 낮추기 위한 설계 원칙

ADP
의존 그래프에 순환이 없어야 한다

DIP / OCP
구체 구현보다 추상화에 의존해 변경 전파를 줄인다

실무 규칙

의존성은 생성자나 파라미터로 명시한다

DI 시점에 유효성 검사를 한다 (Fail Fast)

13. 캡슐화

캡슐화는 변경을 내부에 가두는 기술이다

캡슐화를 통해

내부에서는 관련된 변화가 모이고

외부로는 변경 영향이 퍼지지 않는다

결과

응집도 상승
결합도 감소

14. 정리

좋은 설계는 결국 변경을 관리하는 것이다.

응집도
→ 변경 이유를 한곳에 모은다

결합도
→ 변경 영향이 다른 곳으로 퍼지지 않게 한다

캡슐화
→ 그 변화를 내부에 가둔다

좋은 설계는 변경을 가두는 기술이다
