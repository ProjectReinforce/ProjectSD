


1. "변경할 때 왜 이렇게 힘들지?"
   → 하나 고치면 여기저기 터지는 경험 (공감)
   
   사례 
양방향 의존	A 고치면 B 터지고, B 고치면 A 터짐
책임이 섞인 클래스	무관한 변경이 같은 파일을 건드림
구현에 직접 의존	인터페이스 없이 구체 클래스에 의존하면, 그 클래스의 내부 변경이 호출자까지 전파
전역 상태 / Singleton	어디서든 접근 가능 = 어디서든 변경 가능 = 영향 범위 추적 불가
데이터 중복	같은 정보가 여러 곳에 있으면 하나 바꿀 때 나머지도 전부 찾아서 바꿔야 함

2. "변경을 격리하라" 

모든 버그는 응집도가 낮거나, 결합도가 높다

응집도가 높은 징후: 같은 이유로 바뀌는 코드가 한곳에있다.
응집도가 낮은 징후: 이곳의 역할이 다른곳들에 분산됐다(Shotgun Surgery), 여러 역할이 이곳에 섞여 있다(GodClass)
예방 원칙 : 변경 이유를 한곳에 모은다.
├── godclass 예방 SRP(바뀌는 이유가 하나인 클래스)
└── 데이터 중복 제거(Don't Repeat Yourself)


결합도가 낮은 징후 : 한 곳을 수정해도 다른 곳을 수정할 필요가 없다
결합도가 높은 징후 : Side Effect가 크다.
예방 원칙 : 변경의 영향을 막는다.
├── 단방향 의존(ADP (Acyclic Dependencies Principle)입니다.Robert C. Martin, 패키지 설계 원칙: "의존 그래프에 순환이 있어서는 안 된다")
├── if(DIP || OCP) 추상에 의존. else if  직접의존
├── LSP  if (skill is PassiveSkill) { /* 예외 처리 */ }  // 결합도 상승
└── setter 닫기 (캡슐화)


기타
DI 시점에 유효성검사 (Fail Fast)
의존성은 생성자/파라미터로 명시해라	결합도	숨겨진 의존을 드러내서 관리 가능하게
실패는 결과 타입으로 표현해라	결합도	호출자가 내부 구현(어떤 예외가 터지는지)을 몰라도 됨


응집도가 낮아지는/ 결합도가 높아지는 징후를 무시하고 개발을 하면 기술 부채가 쌓이고 유지보수가 점점 힘들어진다.

결합도, 응집도, 의존 방향,책임, 고/저 수준 모듈, 레이어 경계


변하지 않는 쪽이 고수준, 자주 변하는 쪽이 저수준

	SkillManager
	├── 데미지 계산 → 기획자가 밸런스 패치할 때 바뀜
	└── 이펙트 출력 → 아티스트가 연출 수정할 때 바뀜
	"스킬에 관한 것"은 **주제(topic)**이지 **책임(responsibility)**이 아닙니다. SRP에서 말하는 책임은 **"바뀌는 이유"**입니다.
	"이 클래스를 열게 되는 이유를 나열해봐라. 그 이유들이 서로 무관한가?"
	"무관한 이유로 같은 파일을 반복해서 열게 되면, 그 파일에는 책임이 두 개 이상 있다."
	SkillManager를 여는 이유:
	1. 데미지 공식 변경      ← 밸런스 조정
	2. 이펙트 연출 변경      ← 비주얼 개선
